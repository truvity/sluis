This page lists what sluis v1 does today and where each capability stands in v2. v2 is a from-scratch rewrite, and it reaches parity with v1 before it adds anything new, so this list is the checklist for that.

The list was taken from the v1 documentation at release **v1.79.3**. v1 keeps its own roadmap (releases v1.80 to v1.85), so v1 gains features while v2 is built, and this page grows with it. The v1 release a row was taken from is named here; a feature added in a later v1 release is added to the list when the page is refreshed.

Each row is tracked as a GitHub issue labelled [`parity`](https://github.com/truvity/sluis/issues?q=is%3Aissue+label%3Aparity), in milestone `v2.0-alpha` on the [sluis v2 board](https://github.com/orgs/truvity/projects/9). The **v2 status** column follows that issue.

| v2 status | Meaning |
|---|---|
| Planned | Agreed as part of v2 parity, not started. |
| In progress | Work has started. |
| Done | v2 does what v1 did, covered by a test. |
| Changed | v2 deliberately does it differently; the linked decision says how. |

The links in the v1 documentation column go to the [v1 documentation](/v1/), served under `/v1/`.

Three words are used in a fixed way here and in the v2 issues. A **driver** is the storage or crypto technology behind a port (DynamoDB, KMS, rqlite, PKCS#11). An **integration** is a connector to an external system (Google, GitHub, Slack, Outline, Cloudflare). A **client or relying party** is anything that consumes sluis tokens (sign-in for Kubernetes, AWS, Argo CD, the console, MCP and so on).

## Ports

The storage and platform interfaces sluis depends on, and the drivers behind them. The six rows #797 to #802 carry v2 names (port, driver, transport), where every other row keeps the title of its v1 feature; the mapping of the secrets and export rows stays open until that discussion ends.

**Secrets scope.** sluis stores its own secrets and its integrations' secrets (the `secrets` port) and publishes a small typed set of credentials for consumers (the `export` port). It is not a general secrets engine: it mints scoped credentials rather than storing other people's secrets. File-drop and bucket-drop exports are age-encrypted to the consumer's own recipient, whose key is on its YubiKey, so sluis holds only the public recipient. Bootstrap on the boards uses a sealed-state driver.
