# Upgrade to v1.63

## Purpose

Move an installation from v1.62 to v1.63: one process everywhere, one Lambda function or one Deployment, configured by
one service document `sluis.yaml` (`apiVersion` v3, with `controllers.github` and `controllers.slack`)
([ADR 0037](../../../decisions/0037-one-process-everywhere.md)).

## Preconditions

- The installation runs v1.62 (`.0` or later); to start from older, do [v1.62](v1.62.md) first.
- Binary 1.63 and Pulumi library 1.63 (`MinPackageVersion` 1.63) are applied together, in one apply.
- No data moves: SSM, DynamoDB and S3 are unchanged.
- Ability to change the policy and the audit installation's `workloadIdentity` map ahead of the apply.

## Before you start

- **The one role must be admitted before the function runs.** The policy's `aws` matchers and the audit installation's
  workload map named `<prefix>-github` and `<prefix>-slack`; they must name the role that is now the function's. Looks like:
  the controllers are nobody at the console, sign-in works but a controller pass is refused.
- **`FunctionName` decides whether anything is replaced.** At the default (`sluis`) the function, role, policy and log
  group are replaced under the new name (the new created before the old are deleted, and the old log group's events go with
  it). `FunctionName: "<prefix>-http"` keeps them in place.
- **`SLUIS_ROLE` is refused.** A function that still sets it does not start, saying why. A binary of 1.63 and a 1.62
  library, or the reverse, never run together.
- **Preview before every apply, and read the preview.** Expect the `<prefix>-github` and `<prefix>-slack` functions,
  roles, policies, log groups and invoke configs to be destroyed, and the schedules to be updated, not replaced. Delete
  nothing by hand.
- **Dashboards and alerts that select on the old service names stop matching.** The controllers no longer report
  `service_name` `github-roster` or `slack-roster`; their series carry the one process's service name (the issuer's, as
  before). See [telemetry](../../../reference/sluis/telemetry.md).
- **A controller that cannot start stops the process.** Readiness (`/readyz`) is the whole process, controllers included.
- **Replicas above 1 with a controller need a State every replica shares**: the chart refuses it unless
  `config.ports.adapter` is `dynamodb`.
- **The release's Pulumi library `require` pin is automatic** (`hack/pin-pulumi-require.sh`, see
  [CONTRIBUTING](../../../../CONTRIBUTING.md)): nobody bumps `deploy/pulumi/go.mod` by hand before a tag.
- **The audit catalogue needs its schemas**: the audit writer refuses to start without the `.json` schemas, which ship as
  the release asset `sluis-audit-catalogue_<version>.tar.gz`. Relevant when the audit installation is upgraded with it.
- **N-1 is one release only.** A v2 `serve` document loads unchanged (no controllers), and `sluis controller github|slack`
  still run as processes of their own, deprecated; they are to be removed in a later release (check the CHANGELOG).

## Steps

### 1. Admit the one role in the policy and the audit installation

**Run**: add the new matcher in a policy change that ships first. On Lambda, the `aws` matcher names the function's role
(`<FunctionName>`); on Kubernetes, `exchange` and the audit installation's `workloadIdentity` map admit the one
ServiceAccount `system:serviceaccount:<ns>:<release>`, where they admitted `<release>-github-roster` and
`<release>-slack-roster`.

**Expect**: the old and the new identities are both admitted.

**Verify**: the policy renders (`sluisctl policy render`) and the installation loads it.

**Rollback**: revert the policy change; the old matchers are still there.

### 2. Merge the documents into one v3 document

**Run**: write one service document with `apiVersion: sluis.truvity.github.io/sluis/v3`
(`schemas/config/sluis.schema.json`). The `serve` document's keys stay at the top level. The controllers' `consoleURL`
(unset is `publicURL`), `console.auth.aws.audience`, `tokenFile`, `recordsDir`, `appsDir` (GitHub) or `credentialsDir`
(Slack) and `interval` go under `controllers.github` and `controllers.slack`; an absent one is a controller that is off.
`ports`, `adapters`, `audit`, `secrets`, `policy`, `log` and `probes` are the one document's, and the controllers' copies
are dropped. `policy.file` is required when a controller is named.

```yaml
apiVersion: sluis.truvity.github.io/sluis/v3
issuerURL: https://access.example
publicURL: https://access.example/console
policy: {file: /etc/sluis/policy.yaml}
secrets: {source: ssm, root: /sluis/example}
ports: {adapter: dynamodb, dynamodb: {table: sluis}}
audit: {tokenFile: /var/run/audit/token}
controllers:
  github: {consoleURL: "http://sluis.access.svc:8080/console", interval: 15m}
  slack: {consoleURL: "http://sluis.access.svc:8080/console"}
```

**Expect**: the binary loads it at start; on Lambda the library writes `apiVersion`.

**Verify**: `sluis serve --config <file>` reaches ready.

**Rollback**: put the v2 documents back; v1.63 reads them (N-1).

### 3. Lambda: change the Pulumi arguments and apply

**Run**: in `LambdaArgs`, `Config` is the one v3 document. Remove `GitHubConfig`, `SlackConfig`, `HTTP`, `GitHub`,
`Slack` and `Exports.Function`. Set `Function` (`MemoryMB` default 512, `TimeoutSeconds` default 300) if the defaults do
not fit, and `FunctionName: "<prefix>-http"` to keep the existing resources in place. Read `FunctionArn`, `FunctionName`,
`RoleArn` and `RoleName` where you read the `HTTP|GitHub|Slack` outputs. Preview, read it, apply.

What the library now does: one role `<FunctionName>` with the http role's policy plus the controllers' needs (credentials
and exports read/write, config read, the signing keys, `lambda:InvokeFunction` on the function itself,
`sts:GetWebIdentityToken` restricted by `WebIdentityAudience`); no denials, so the keyring is writable by the one role. The
controllers' code runs with those permissions (per-role isolation is gone by decision). The scheduler role may invoke only
the function. The function takes API Gateway events, `{"kind":"tick"|"run","target":"<id>"}`,
`{"kind":"refresh"}` and `{"kind":"exports"}`; controllers do not loop on Lambda.

**Expect**: the `<prefix>-github` and `<prefix>-slack` resources are destroyed; the schedules keep their names and point at
the one function.

**Verify**: `aws lambda list-functions` shows one function of the instance; a `{"kind":"tick","target":"<org>"}` test invoke
returns `"outcome":"ran"`; the sign-in page loads.

**Rollback**: apply the v1.62 library and zip with the three documents. The old log group events are gone if the function
was replaced. SSM, DynamoDB and S3 are unchanged, so no data to restore.

### 4. EKS identity: one role for the one pod

**Run**: for `NewKubernetesIdentity`, `ServiceAccount` (required) and `Description` are on the args; the `Serve`, `GitHub`,
`Slack` and `ProcessArgs` are gone. The role is `<prefix>-sluis` (was `<prefix>-sluis-serve`) with one Pod Identity
association for the one ServiceAccount. Outputs are `RoleArn` and `RoleName` (were `ServeRoleArn`, `GitHubRoleArn`,
`SlackRoleArn`). Its policy is the old serve role's plus, with the new `Instance` (and `Region`, `ParameterKeyArn`), the
Lambda role's SSM grants under `/sluis/<instance>/`. Do this in a quiet window.

**Expect**: Pulumi replaces the serve role under its new name and destroys the github and slack roles and associations.

**Verify**: the pod's AWS calls succeed (the signing key, DynamoDB, SSM).

**Rollback**: apply the v1.62 library; Pulumi recreates the three roles.

### 5. Kubernetes: `helm upgrade` to one Deployment

**Run**: move each controller's values to `config.controllers.github` / `config.controllers.slack` (present is on:
`consoleURL`, `interval`, `tokenFile`, `appsDir` or `credentialsDir`, `recordsDir`). Delete `controllerGithub` and
`controllerSlack` (refused at render if left). Then `helm upgrade`.

| Value | Replacement |
|---|---|
| `controllerGithub.enabled`, `controllerGithub.config` | `config.controllers.github` |
| `controllerSlack.enabled`, `controllerSlack.config` | `config.controllers.slack` |
| `controller{Github,Slack}.config.{policy,release,log,ports,platform,preset,adapters,audit,probes}` | the service document's own keys, shared by the controllers |
| `controller{Github,Slack}.{replicas,strategy,minReadySeconds,podDisruptionBudget,resources}` | `replicaCount`, `strategy`, `minReadySeconds`, `podDisruptionBudget`, `resources` (the one Deployment's) |

The Deployments, ServiceAccounts, ConfigMaps (`<release>-github-roster-config`, `<release>-slack-roster-config`) and
PodDisruptionBudgets of the controllers are deleted by the upgrade; the controllers run as the release's own
ServiceAccount, which gets the controllers' Role. Refused at render: a controller with `replicaCount` above 1 unless
`config.ports.adapter` is `dynamodb`; a controller without `exchange.clusters`, `console.mount` or the console's own
Service as `consoleURL`; a `tokenFile`, `appsDir`, `credentialsDir` or `recordsDir` the chart does not mount. The chart's
checksum annotations are two (`checksum/config`, `checksum/policy`).

**Expect**: one Deployment `<release>`; the two controller Deployments gone.

**Verify**: `kubectl -n <ns> get deploy` shows one; `/readyz` is ready; the console shows both controllers' last passes.

**Rollback**: `helm rollback` to the v1.62 release; the controller objects return.

### 6. Update telemetry consumers

**Run**: change dashboards and alerts that select `service_name` `github-roster` or `slack-roster` to select the one process's service name.

**Expect**: series for the controllers appear under the one name.

**Verify**: the dashboards show data after the rollout.

**Rollback**: revert the dashboard change.

## Afterwards

- Check the next scheduled tick of each target ran, and the audit trail has the controllers' records.
- Tell the audit installation's owners and the policy's owners that the controllers are one identity now.
- Next: [upgrade to v1.64](v1.64.md).
