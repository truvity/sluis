# Upgrade to v1.77.1

v1.77.1 removes storage layout v4 and everything that moved an installation off it, as [ADR 0072](../../../decisions/0072-storage-layout-v5-module-first.md) decided. An installation that runs v1.77.0 on layout v5, with the v4 resources cleaned up, upgrades by deleting the switches it no longer needs. History is in the [CHANGELOG](../../../../CHANGELOG.md).

## Before you start

The installation must already be on layout v5, on v1.77.0 or earlier. v1.77.1 can neither read layout v4 nor migrate from it.

| Check | Expected |
|---|---|
| the service document's `secrets` (source `ssm`) | `layout: v5` |
| `ports.dynamodb` (or `adapters.state.settings`) | `tables`, one per module; no `table` |
| the DynamoDB tables | the module tables (`sluis-<instance>-<module>` by default); the v4 table is no longer declared, or was retired with `Compat.RetireLegacyTable` |
| the v4 SSM parameters | gone: nothing under `<root>/internal/config/` or `<root>/internal/credentials/` |
| the Pulumi program | `Layout: LayoutV5` (or `"v5"`), and no `Compat` other than the retirement above |

An installation still on layout v4 migrates with the v1.77.0 binary and library first: [upgrade to v1.75](v1.75.md) step by step, then [v1.76](v1.76.md), then run `sluis migrate v5 prune` of v1.77.0.

List what is left of layout v4 (names only):

```sh
root=/sluis/<instance>
for prefix in "$root/internal/config/" "$root/internal/credentials/"; do
  aws ssm describe-parameters \
    --parameter-filters "Key=Name,Option=BeginsWith,Values=$prefix" \
    --query 'Parameters[].Name' --output text
done
```

A parameter listed there is read by nothing on v1.77.1. Delete it with `sluis migrate v5 prune` of v1.77.0 before upgrading, or by name afterwards (`aws ssm delete-parameters --names ...`): v1.77.1 has no command that does.

## What was removed

| Removed | Use instead |
|---|---|
| secrets layout v4 (`secrets.layout: v4`) | `secrets.layout: v5` |
| an `ssm` `secrets` section with no `layout`, which meant v4 | `layout: v5`, now required with `source: ssm` |
| the single DynamoDB table: `ports.dynamodb.table`, `adapters.state.settings.table`, the installation's `aws.table` | `ports.dynamodb.tables` (or `adapters.state.settings.tables`), one table per module |
| `sluis migrate v5` (`plan`, `copy`, `verify`, `prune`) | none: run it with v1.77.0 |
| `sluis migrate --skip directory` | `--skip google` |
| `sluis serve` | `sluis issuer`, with the same `--config` |
| Pulumi `Layout` (`LayoutV4`, `LayoutV5`, `LayoutV4V5`) on `LambdaArgs` and `RoleArgs` | nothing: the library is layout v5 |
| Pulumi `CompatArgs`, and `Compat` on `LambdaArgs` and `StatesArgs` | nothing: the v4 parameters and the v4 table are not declared |
| Pulumi legacy and single table: `StatesArgs.Legacy`, `LegacyStateArgs`, `States.Legacy`, `States.LegacyBackupArn`, `LegacyBackupArnOutput`, `LegacyBackupRetentionDays`, `NewState`, `StateArgs`, `State`, `StateType`, `StateGrant.TableArn`, `PortsArgs.TableName` | `NewStates` and `States.Grant()`: a table per module |
| Pulumi `LambdaArgs.MigrationRoleArn` | nothing: it was the role `sluis migrate v5` ran as |
| Pulumi `KeyPolicyArgs.Layout` | nothing |
| Pulumi `StateSecretParameterName`, `RecoveryPasswordParameterName`, `ConfigParameterPrefix` (layout v4 names) | `StateSecretParameterNameV5` and the other `...V5` names |

The service and the library refuse each removed key by name; a document that names one does not load.

## 1. Update the Pulumi program

Delete the switches; what they selected is now what the library does.

```diff
 args := &sluispulumi.LambdaArgs{
 	...
-	Layout: sluispulumi.LayoutV5,
 }
 roles := sluispulumi.RoleArgs{
 	...
-	Layout: sluispulumi.LayoutV5,
 }
```

| Also delete | Because |
|---|---|
| `TableArn` in a `StateGrant` you build by hand | the field is gone; `States.Grant()` gives `Tables` |
| `Compat`, `MigrationRoleArn`, `Legacy` on `StatesArgs` | the fields are gone |
| a constant built from `ConfigParameterPrefix` or `StateSecretParameterName` | they named `internal/config/...`, which a layout v5 process never reads |

A layout v5 installation's preview with the v1.77.1 library shows no change.

## 2. Update the documents and command lines

| Where | Change |
|---|---|
| a service or module document with `secrets: {source: ssm}` | add `layout: v5` if it was left out (the Pulumi library already writes it on Lambda) |
| `ports.dynamodb.table`, `aws.table`, `adapters.state.settings.table` | name the module tables in `tables` |
| a Deployment or a script that runs `sluis serve` | `sluis issuer` |
| `sluis migrate --skip directory` | `--skip google` |

## 3. Kubernetes with another secrets store

An installation whose secrets are not on SSM (the `openbao` or `memory` Secrets adapter) keeps the credentials sluis writes in that store. Their paths followed the layout v4 kinds and now follow the layout v5 address, the module first:

| Credential | Before | v1.77.1 |
|---|---|---|
| a Google Workspace's key | `credentials/directory/google/<id>/<ref>` | `credentials/google/workspace/<id>/<ref>` |
| an organisation's App key | `credentials/github-org/<org>/<ref>` | `credentials/github/org/<org>/<ref>` |
| the link App | `credentials/github-app/link/<ref>` | `credentials/github/app/link/<ref>` |
| a catalogue GitHub App | `credentials/github-app/<id>/<ref>` | `credentials/github/app/<id>/<ref>` |
| a runner App | `credentials/github-runner-app/<tier>/<org>/<ref>` | `credentials/github/app/runner-<tier>-<org>/<ref>` |
| a person's GitHub link | `credentials/github-link/<account>/<ref>` | `credentials/github/link/<account>/<ref>` |
| a Slack workspace | `credentials/slack-workspace/<team>/<ref>` | `credentials/slack/workspace/<team>/<ref>` |
| a Slack App | `credentials/slack-app/<id>/<ref>` | `credentials/slack/app/<id>/<ref>` |
| the console's session key | `credentials/console/session-key` | `credentials/oidc/console/session-key` |

The records in State name only the `<ref>`, so copy each secret to its new path in the store, keeping the `<ref>`, before the new version starts; a credential that is not copied reads as absent and its connection must be made again. A generated client's record (`credentials/oidc-client/<id>/secret`) does not move. Such an installation on DynamoDB names `ports.dynamodb.tables` as well: the single table is gone on every platform.

## 4. Roll

Roll the service and the module functions or Deployments together with the library: the documents the v1.77.1 library writes are the ones a v1.77.0 service already reads, and the reverse holds for a layout v5 installation, so the order within the release does not matter.

## Roll back

Roll back to v1.77.0 with the same documents: v1.77.1 writes nothing v1.77.0 cannot read. On Kubernetes with another secrets store (step 3), copy the credentials back to their old paths first.
