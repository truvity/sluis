# Upgrade to v1.75

v1.75 removes secrets layout v3, `transition` and `sluis migrate secrets-layout`. Run `secrets.layout: v4` first; an installation on v3 or `transition` moves on v1.74.x ([steps](../migrate/migrate-secrets-layout.md)).

## The Pulumi library

The first v1.75 apply adopts the v4 copies `sluis migrate` wrote at `/sluis/<instance>/internal/config/issuer/state-secret` and `.../recovery/password`. It deletes the `private/config` ones after the function is updated, and the roles lose their grants on `private/*`. Values stay.

Read the preview first: two parameters created, two deleted, no replacement.

## Move to layout v5

Layout v5 splits storage by module ([layout](../../../reference/sluis/storage-layout.md)). Writes freeze 10 to 15 minutes.

Before you start:

- Run v1.75 with the Pulumi library on `Layout: "v4"`.
- `controllers.github.appRefs` is optional.
- Give no catalogue App the id `link` or `runner-...`.
- Keep the KMS key, alias and instance name.

1. Add the v5 tables and apply.

   ```go
   Layout: "v4+v5",
   ```

   Expect 2 parameters created and role updates ([layouts](../../../reference/sluis/pulumi-library.md#layouts)).

   The plan refuses v5 parameters an older library wrote as plain values: apply this release first.

2. Plan. Nothing may be refused.

   ```sh
   sluis migrate v5 plan --from v4.yaml --to v5.yaml
   ```

3. Copy live, dry run first.

   ```sh
   sluis migrate v5 copy --skip issuer --dry-run --from v4.yaml --to v5.yaml
   sluis migrate v5 copy --skip issuer --from v4.yaml --to v5.yaml
   ```

4. Freeze the source; keep the issuer up and Lambda concurrency as is ([how](../../../concepts/sluis/migration-freeze.md)).

   ```sh
   sluis maintenance on --reason "layout v5" --config v4.yaml
   ```

5. Copy the changes and the issuer, then verify.

   ```sh
   sluis migrate v5 copy --overwrite --from v4.yaml --to v5.yaml
   sluis migrate v5 verify --from v4.yaml --to v5.yaml
   ```

6. Rename a blob credential: `internal/blobs/<name>` is `internal/google/blobs-<name>` on v5. Set `CredentialsRef` to that: every process reads it there; copied ones stay. Then set the layout and apply ([document](../../../reference/sluis/pulumi-library.md#layouts)).

   ```go
   Layout: "v5",
   ```

7. Sign in, compare the `kid` set, and check.

   ```sh
   curl -s https://login.example/keys | jq -r '.keys[].kid'
   sluis check --config v5.yaml
   sluis maintenance off --config v4.yaml
   ```

## Roll back

- Never start the v1.75 issuer on v5 before the copy; if it started, copy with `--overwrite`.
- Within 7 days, a return to v4 loses v5's refresh rotations.
- Run `sluis maintenance off` before restarting v4.

## After 7 days

1. Prune the v4 parameters. The dry run lists what goes and stays, with a plan hash, and refuses unless every v4 item is `same` on v5.

   ```sh
   sluis migrate v5 prune --dry-run --from v4.yaml --to v5.yaml
   sluis migrate v5 prune --confirm-plan <hash> --from v4.yaml --to v5.yaml
   ```

2. Set `Compat.DropV4` and apply. The 2 Pulumi-owned v4 parameters are deleted.

3. Add `RetireLegacyTable` to `Compat` on `StatesArgs` and the function, and apply. The legacy table is exported for 30 days (`legacyTableBackupArn`) and unprotected.

4. Remove `Legacy` from `StatesArgs` and apply. The table is deleted.

5. `aws ssm get-parameters-by-path --recursive` on the v4 prefixes must list only the kept ones.

6. On an S3 blob store, delete the blobs that sat at the root of the bucket before v1.75. The controllers' reports are now under the module's prefix (`github/reports/`, `slack/reports/`) and the hub's cache under `google/cache/`, so the function role needs no grant beyond its module's. The first controller pass writes the reports again, so nothing is copied. `prune` works on parameters and does not touch the bucket, so this is by hand (add the installation's blob `prefix`, if it has one):

   ```sh
   aws s3 rm --recursive s3://<bucket>/reports/github/
   aws s3 rm --recursive s3://<bucket>/reports/slack/
   aws s3 rm --recursive s3://<bucket>/snapshots/
   ```
