# Upgrade to v1.62

## Purpose

Move an installation from v1.61 or older to v1.62: four versioned documents, secrets by name, SSM layout v3 under
`/sluis/<instance>`, and on Lambda the release zip deployed unchanged with the configuration as a layer
([ADR 0036](../../../decisions/0036-configuration-is-immutable-per-instance.md)).

## Preconditions

- The installation runs v1.61.x (v1.61.1 or later on Lambda).
- Binary 1.62 and the Pulumi library 1.62 deploy together; neither works alone on Lambda.
- On Lambda, the release zip and its SHA-256 (`LambdaArgs.PackageSHA256`, a reviewed pin in the stack's source).
- AWS credentials that can read and write `/sluis/*` in SSM, and for the credentials copy, the access `sluis migrate` needs
  ([migrate state](../migrate/migrate-state.md)).
- Prefer a quiet window: the signing-key retirement (step 6) is its own window, at low traffic.

## Before you start

- **Binary and library move together.** A v1.62 binary refuses the v1.61 library's environment (`SLUIS_CONFIG_FILE`,
  `SLUIS_SECRET_FILES`, `ssm:<path>` variables) and will not start on a function deployed that way. The library refuses a
  package older than its own minor. Looks like: the function fails at start and names the v1.62 library.
- **Preview before every apply, and read the preview.** `pulumi preview` must show the layer, the functions' code and the
  IAM changes you expect and no replaced key.
- **Retiring the asymmetric keys drops their key ids from the JWKS at once.** A token they signed and still in flight can
  fail to verify. It is a step of its own (6), not part of the apply that moves to 1.62.
- **Deleting keys needs state surgery.** The old keys are protected in the stack: `pulumi state delete` (preferred), or
  `pulumi state unprotect`. See step 6.
- **A v1 document keeps working until you move it.** A v1.62 binary reads v1 and v2 documents, so the binary can roll
  first and the configuration second; a v1 document that names no root keeps SSM layout v2 (`/sluis`) until it moves.
- **The release's Pulumi library `require` pin is automatic** (`hack/pin-pulumi-require.sh`, see
  [CONTRIBUTING](../../../../CONTRIBUTING.md)): nobody bumps `deploy/pulumi/go.mod` by hand before a tag.
- **Configuration is read once, at start.** A change to a document is a new instance (a new pod, a new layer version).

## Steps

### 1. Render the policy

**Run**: `sluisctl policy render <file or directory> -o policy.yaml`. It merges v1 policy files, access documents and
`policy/v2` fragments into the one canonical policy document, held to every check the service runs at start. Name the
result in each service document's `policy.file`. Until then a v1 document keeps working.

**Expect**: exit 0 and a `policy.yaml` with `apiVersion: sluis.truvity.github.io/policy/v2`.

**Verify**: re-run the render and compare; the output is deterministic.

**Rollback**: none, because nothing deployed changed; delete the file.

### 2. Move the keys out of the service documents

**Run**: edit each service document to `apiVersion: sluis.truvity.github.io/<document>/v2`. Moved into the policy
document, as values and not files:

- `exchange.clustersFile` to `exchange.clusters`; `exchange.awsFile` to `exchange.aws`; `github.owners` to
  `exchange.github.owners`;
- `github.runnerTiers` to `apps.github.runnerTiers`; `github.catalogueFile` (and the GitHub controller's `catalogueFile`)
  to `apps.github.catalogue`; `slack.catalogueFile` to `apps.slack.catalogue`;
- `enabledOrgs` / `enabledWorkspaces` to `controllers.github.enabledOrgs` / `controllers.slack.enabledWorkspaces`;
- `policyDir` to `policy.file`; `overlayFile` becomes `directory.workspaces`; `api` is removed.

Secrets are named, not pointed at: `valkey.passwordSecret`, `recovery.passwordSecret`, `signingKey.kms.stateSecret` and
`signingKey.kmsWrapped.stateSecret` (`issuer/state-secret`), a workspace's `keySecret` (`directory/<id>/key`),
`oauthClient.provider`. Add `secrets: {source: env | file | ssm, root}`. The retired keys (`valkey.passwordEnv`,
`oauthClient.idFile|secretFile|secretEnv`, `adminPasswordEnv`, `recovery.passwordFile`, `clientSecretsDir`,
`...stateSecretFile`, `directory.workspaces[].keyFile`) are refused in a v2 document with where they went.

**Expect**: the binary starts on the document; a v2 document that names a retired key is refused with where it went.

**Verify**: `sluis serve --config <file>` validates at start (or run the Lambda test invoke after step 5).

**Rollback**: put the v1 document back; the v1.62 binary still reads it.

### 3. Copy the configuration secrets to the instance root

**Run**:

```sh
sluis migrate ssm-layout --to-root /sluis/<instance> --dry-run
sluis migrate ssm-layout --to-root /sluis/<instance>
```

It renames `oauth/client-id` and `client-secret` to `providers/google/default/client-id` and `client-secret`, and
`clients/<id>` to `clients/<id>/secret`. The old parameters stay until step 7.

**Expect**: a JSON report that names parameters and never a value.

**Verify**: `aws ssm get-parameters-by-path --path /sluis/<instance>/private/config/ --query 'Parameters[].Name'` lists the
names; the dry run's report matches the real run's.

**Rollback**: delete the new parameters; the old ones were not touched.

### 4. Copy the credentials

**Run**: `sluis migrate --from <config whose Secrets adapter names /sluis> --to <config whose names /sluis/<instance>>`
([migrate state](../migrate/migrate-state.md)). The exports are written again by the next exports pass.

**Expect**: a report with `ok: true`.

**Verify**: `totals.verified` equals `totals.source`.

**Rollback**: none needed; the source is not changed. Delete the copies under the new root to start over.

### 5. Apply the v1.62 library and binary

**Run**: on Lambda, set `PackageSHA256` (required), `Instance` (the SSM root `/sluis/<instance>`; not `private` or
`export`) and the documents; preview, read it, apply. On Kubernetes, `helm upgrade` with the chart values below. Keep the
signing keys as they are in this apply.

Library changes in this apply (Lambda):

- the functions' code is the release zip byte for byte; the three service documents and the policy (checked by sluis's
  own loader) are published as one `<prefix>-config` Lambda layer, mounted last at `/opt/sluis`. A change publishes a new
  layer version and updates the functions; old versions are kept, so a rollback is re-pointing;
- the environment is `SLUIS_ROLE`, `SLUIS_CONFIG=/opt/sluis/<role>.yaml` and `OTEL_*`; `SLUIS_CONFIG_FILE`,
  `SLUIS_SECRET_FILES` and the `ssm:<path>` variables are retired and refused;
- the state secret and recovery password are generated at
  `/sluis/<instance>/private/config/{issuer/state-secret,recovery/password}`;
- IAM: every function reads and writes `<root>/private/credentials/*` and `<root>/export/*`; only the http function reads
  `<root>/private/config/*`, which the controllers are denied;
- refused in the published documents: any `endpoint` (unless `AllowEndpoints`, a LocalStack test);
- removed: `Catalogues`, `CataloguePaths`, `Env`, `FunctionArgs.Env`, `FunctionArgs.SecretFiles`, `SecretFile`,
  `ConfigFilePath`, `StateSecretPath`, `RecoveryPasswordPath`, `WrappedSigningArgs.KeepRemoteSigningKeys`.

Chart changes in this apply: the chart renders four documents; the clusters, AWS, overlay and catalogue ConfigMaps are
gone, folded into `policy`. The secrets the config names are projected as files under `/var/run/sluis/secrets` from the
`secrets` value (`{name, secretName, key}`), and `config.secrets` must be `{source: file, root: /var/run/sluis/secrets}`
(the default). `config.policy.file` must be the path the chart mounts. Removed values and where they went:

| Value | Replacement |
|---|---|
| `access`, `overlay` | render the access document first, `sluisctl policy render <dir>`, and pass the result as `policy` |
| `directory.workspaces` (`backend`, `admin`, `secretName`, `secretKey`, `id`, `serve`, `syncGroups`) | `config.directory.workspaces` with `keySecret: directory/<id>/key`, the key projected by a `secrets` entry |
| `config.clientSecretsDir` | none: `config.secrets` (the default) |
| `config.exchange.clustersFile`, `.awsFile` | `exchange.clusters`, `exchange.aws`, or `policy.exchange` |
| `config.github.*`, `config.slack.catalogueFile`, `config.exports` | `policy.exchange.github.owners`, `policy.apps.github.runnerTiers`, `githubApps.catalogue` / `slackApps` (or `policy.apps`), `policy.exports` |
| `controllerGithub.config.enabledOrgs`, `.catalogueFile`; `controllerSlack.config.enabledWorkspaces` | `policy.controllers.github.enabledOrgs`; the policy's catalogue; `policy.controllers.slack.enabledWorkspaces` |
| `config.policyDir`, each controller's `config.policyDir` | `config.policy.file` |

**Expect**: the preview shows the layer version, the function code updates and IAM changes only.

**Verify**: a sign-in works; on Lambda, `{"kind":"tick","target":"<org>"}` test invokes return `"outcome":"ran"`.

**Rollback**: re-point the functions at the previous layer version and the v1.61 zip with the v1.61 library; the old
`/sluis` parameters are still there.

### 6. Retire the asymmetric signing keys (only when moving from `kms` to `WrappedSigning`)

Do this as its own step, at low traffic, after step 5 has been healthy. With `WrappedSigning` the library no longer
declares the two asymmetric keys (a `Config` naming `signingKey.kms` beside it is refused), and they are protected in the
stack.

**Run**:

1. Record both key ids (`pulumi stack output`, or `aws kms describe-key` on the aliases). You need them to roll back.
2. `pulumi state delete` `<name>-signing-key` and `<name>-signing-key-rs256` and their aliases, then apply with
   `WrappedSigning`. The keys stay in AWS untouched.
3. `aws kms disable-key` each old key. Only after `lifetimes.token` and the longest JWKS cache among the verifiers have
   passed, `aws kms schedule-key-deletion` (30 days of grace at least).

**Expect**: the JWKS no longer publishes the old key ids.

**Verify**: a fresh token verifies at a relying party; a token minted before the switch has expired.

**Rollback**: while the keys exist, `aws kms cancel-key-deletion`, `aws kms enable-key`, `pulumi import` the keys and
aliases, and apply without `WrappedSigning`.

The alternative, `pulumi state unprotect` on the two keys and an apply, schedules their deletion at once with the 30-day
window. It is simpler, but the deletion schedule disables the keys and there is no step at which to stop and look. Prefer
the first.

### 7. Delete the v2 parameters

**Run**: delete the parameters under `/sluis/private` and `/sluis/export` once the installation runs on v3 documents
and has been healthy for as long as you want a cheap rollback.

**Expect**: nothing reads them.

**Verify**: sign-in and an exports pass still work.

**Rollback**: none, because the values are gone; step 3 and 4 can be re-run from a backup of the parameters only, so take
one first.

## Afterwards

- Check the next exports pass wrote `<root>/export/*`.
- Run the telemetry and audit checks of the installation; the `signingKeyRotationStalled` alert should be quiet.
- Tell the people who own a relying party that caches the JWKS if you did step 6.
- Next: [upgrade to v1.63](v1.63.md).
