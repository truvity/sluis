This is the target state, not a running system. Every role writes its records to a durable outbox and moves on. One writer turns them into ordered batches in an object-storage archive, a separate notary seals the batches, and each node keeps a search index fed from the same ordered batch stream. The page is drawn from `site/src/data/explorer/audit.yaml`, which today is written by hand from the design; once the permission manifest exists, the roles, sockets and call edges are generated from it. The ideas behind the page are on [Audit](/concepts/audit/); the roles are described under [Roles](/concepts/roles/).

The same roles, the same records and the same integrity chain run on every shape. Only the drivers behind the outbox, key, state, blob and index ports change. Pick a shape; the map, the flows, the sockets and the outage table follow it. Without script the page shows T4 and every table is plain HTML.

## The outbox port

A request returns once its audit record is durable in the outbox, never waiting for the writer. The port has three calls, Append for producers and Receive and Ack for the writer. One contract; the driver behind it depends on the shape. The outbox may deliver out of order, twice or late: the sequence is made later, when the writer registers a batch, and the writer dedupes by record id.

<AuditExplorer part="outbox" />

The audit outbox is a local spool on servers, co-signed in cluster mode, and an SQS queue on Lambda. Kubernetes: later. The recovery path is separate: it spools locally on every shape and never blocks.

## The integrity chain

How an auditor can tell that nothing was removed, changed or added. The notary signs batch heads, which form a hash chain, and verification never trusts the index or the state.

<AuditExplorer part="chain" />

<Proposed>
The state store sits on the write path of every batch. This is acceptable given the outbox, a reconciler that compares the bucket listing with `audit_batches`, and verification that reads the archive and the seals only.
</Proposed>

## Index and lag

<AuditExplorer part="lag" />

A node keeps its index in a file on servers. Lambda ships no index: `audit-read` and its index run in a separate audit install that reads the same bucket, on Kubernetes with Postgres or on a server with `sqlite`. The index is a rebuildable cache; the chain in the bucket is the record.
