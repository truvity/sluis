# Changelog

## Unreleased

- An `AuditLog` document must name its `lock_mode`, and it must be `none`, `removable` or `compliance` (ADR 0029, "Lock modes"; REQ-AUDIT-008). store@ refuses a document with none, an empty one or any other word, and the writer does not start on one; before, any text was taken. The local installation declares `none`, so only a hand-written `AuditLog` without the line needs it added.
- `just build-cli` builds the `sluis` command into `bin/sluis` with the release build's version stamp, and `bin/` is on `PATH` inside devbox, so `sluis` there is the build of this checkout. Before a build the command is not found.
- The start and reload facts of store@ now reach the audit log. They carried the documents in force as one string, `Kind:seq:sha384` joined by `;`, and a record string holds 1024 bytes, so the emitter refused the fact for the ten documents of the local installation and of the boards (`audit emit failed ... invalid_argument: bound` in the journal of store@) and the fact was counted as lost. The field `unmapped.sluis.documents` is now an object with a member for each kind, `{"<Kind>": {"seq": n, "sha384": "<hex>"}}`, in the one record of the start or of the reload; a set has one document of a kind, so the record is about 5 KB for all 34 config kinds, in a limit of 16 KB. The same shape in key@ is fixed: a KeyPlan that lists recipients with no key was reported as one fact with their thumbprints joined, which passes 1024 bytes at 24 recipients, and is now one fact for each recipient (REQ-DATA-085).
- `sluis config check --against OLD` compares the bootstrap file with the previous one and prints a `warn` line for each setting that was added, changed or removed, with its path and never its value, because a changed bootstrap file is a restart of store@; a previous file that cannot be read fails the check (REQ-OPS-130). `--live` of `config check` and `config explain` is now a known flag that answers a usage error (exit 2) and runs nothing: this version has no console API for it to read through. In CI the tests of `sluis config check` that run the real store executable fail, and no longer skip, when `cargo` is missing.
- The Rust toolchain is no longer installed by the first `cargo`, and the flake "failed to install component: 'clippy-preview-...', detected conflict: 'bin/cargo-clippy'" is gone (it failed jobs of `advisories`, `code`, `deny` and `os-containers` and the first cargo of a new worktree). Cause: the first `devbox run` of a checkout makes `.venv`, pip runs `rustc --version` with a timeout of 0.5 s for its user agent, that `rustc` was rustup's and installed the pinned toolchain by itself, and pip killed it half way, which left a toolchain that rustup could neither use nor complete. `devbox.json` now sets `RUSTUP_AUTO_INSTALL=0`; `just rust-toolchain` installs the toolchain, under a lock, and names and removes a half-made one; the recipes that run cargo depend on it, and the `advisories` job runs it like the other jobs. A bare `devbox run -- cargo ...` in a checkout that has no toolchain yet now says the toolchain is not installed; run `devbox run -- just rust-toolchain` once, or any recipe that builds Rust.
- A restore or a reset of the change log can no longer make a saved resume point skip changes without a word (issue 1459; ADR 0005, REQ-DATA-114 to REQ-DATA-119). A resume point is now a pair: the epoch of the change log and a sequence in it. The driver draws a nonzero random epoch when it creates the log (rqlite keeps it in the `<namespace>_meta` table, beside the log, so every node reads one value), a log made again has another, and a listing and every message of a watch name it (`ListResponse.log_epoch`, `WatchResponse.log_epoch`, `WatchRequest.log_epoch`; `QueryResponse.log_epoch` and `TailLogRequest.log_epoch` on the item port). store@ refuses a watch from a nonzero resume point under another epoch, or none, as `resume_point_expired`, even when the new log has grown past the number, and the watcher lists the kind again. **Breaking:** a resume point saved without an epoch is refused once and the watcher lists (there is no v2 release to keep working); in the Rust client `WatchOpts::from` takes a `ResumePoint { epoch, sequence }` and the events carry one, which an `ExportCursor` must save whole; the item port's `TailLog` from a nonzero sequence needs the epoch, so deploy store@ and the driver together. A log table made again alone also starts with a floor of 0, so a trim of the old log does not hide the first rows of the new one. Loading an older rqlite database file back is still not detected from inside the log: delete the `log_epoch` row of `<namespace>_meta` before the driver starts, and it draws a new epoch.
- **Breaking:** the `AuditLog` config document must declare `lock_mode`, one of `none`, `removable` or `compliance`; store@ refuses a document without one, or with another value, at load (it took any text, and an empty one). Add `lock_mode:` to the document and sign it again. `sluis config check` prints a `lock-mode` line that reports the declared mode (REQ-AUDIT-028, partial: no file names the blob driver yet, so the mode is the declared one and is not compared with the driver's). The local installation's document already declares `none`.
- The reader checks the envelope of every entry it opens against the record (ADR 0029; REQ-AUDIT-153, which now names the indexer and the reader). It used to compare only the entry's record id and tenant with the index row and the record's hash with the row's, so an entry whose clear envelope lied about the record (a time, a class, an activity, a status, an actor type, the record id, the tenant, or a record that names another boundary) was returned if an index row pointed at it. The indexer refuses such an entry when it indexes it, so only a forged or an old index can point at one. A search that reaches such an entry is now refused as `internal` with the reason `integrity` and the field path `envelope`, is audited as a failed `reader.search`, and returns no record; a search that does not reach it is answered, and nothing else in the reader stops. Nothing else changes.
- `sluis config check` and store@ refuse a KeyPlan whose card slot map is wrong, by the slot map rules that key@'s check shares with them (the rules common to all stores; a card adds limits that only key@'s check applies, such as no override of a card's default slot): two purposes in one slot, an enabled card-key purpose with no slot, a slot that is no slot of a board (9e, 96, upper case), or a purpose listed twice. The check line is the `set` line and it names the entry (`KeyPlan: card slot map: default.purposes[1].slot: shared with wrapping`) and no key. A purpose the plan does not list needs no slot. A KeyPlan that key@ would refuse at its start is now refused at the config check, and by store@ at a reload; **a plan already loaded that breaks these rules makes store@ refuse to start at its next restart**, not only at a reload (REQ-PKI-037, REQ-PKI-038, REQ-PKI-042; `sluis key request` does not make the check yet).
- The audit emitters make the loss of a best-effort fact visible in the log (ADR 0029, "Facts that are lost are counted"; REQ-AUDIT-186). With the spool full or absent, a fact emitted without waiting (a refusal, a denial, a start, a data-key creation, a wrap write, a revocation, a change of the signer's ring, a failed step of `session`) was dropped with only a journal line as evidence. The Go and Rust emitters now keep, for each tenant, a running total of the best-effort emits that failed, and a record of that tenant carries `unmapped.sluis.lost` (`process`, `total`, `since` in milliseconds) until a record that carried the current total is delivered; a reader takes the highest total per actor, tenant and process and never sums. A record carries only its own tenant's note. A process that exits or restarts while it holds an unreported total loses it, and a quiet actor reports nothing; each report is also a WARN in the process's log, and `Lost()` (Go) and `lost()` (Rust) return the total for an actor to export. New calls: `EmitRequired` / `emit_required` for a caller that fails its operation on an error (the successes of `session`, `exchange` and the upstream adapter: not counted; their refusals and failures stay best effort and are counted), and `EmitBlockingBestEffort` / `emit_blocking_best_effort` for key@'s revocation and the signer's ring change, which wait for their fact and carry on without it. A caller can no longer write `unmapped.sluis.lost`. **REQ-AUDIT-033 is weakened:** it said an emitter "MUST NOT drop records"; it now says the emitter returns the transport's failure and keeps no record in memory, because a full spool leaves no durable place and ADR 0028 rejected buffering and failing every operation. REQ-AUDIT-015 is narrowed to credential issuance, which fails when its fact is not accepted; tightening changes are exempt, because a full spool must never block a revocation.
- **Breaking:** store@ and `sluis config check` refuse a client whose `requires` names a grant that the boundary's `GrantVocabulary` does not declare (a role, a thing or a scope nobody wrote, a name of two parts, a wildcard), with the client and the position (`sluis-cli.requires[1]: not a grant name the vocabulary declares`) and never the value. Before, `policy` left such a name out of the client's `requires` without a word. A vocabulary that `policy` refuses is now refused by the set check too, whether or not the set declares a client. `policy` also refuses, at a decision, a client or a requester whose `requires` holds an undeclared name (`invalid`, path `client.requires` or `requester.requires`), where it used to leave the name out, so a policy that tests `resource.requires.isEmpty()` cannot match a client whose only requirement was a typo. Fix the name in `InstallationClient`, or declare it in the vocabulary (REQ-POLICY-010). The reader of the vocabulary moved to a kit, `kits/rust/sluis-vocab`, that `policy` and store@ share; nothing else changes in `policy`.
- The audit writer no longer feeds itself. It asked policy for a grant in every batch, policy writes one `policy.decide` record for every decision, and that record was the next batch, so a board with no traffic sealed a batch every 5 s: 10 records and 10 card signatures a minute (14,400 signatures and about 200,000 record ids a day, MEASURED 2026-11-07). The writer now keeps the grant for its life less 10 s, as ADR 0007 says a grant is reusable for about 60 seconds: from one record it seals twice (the record and the record of its decision) and then goes quiet, 0 records and 0 signatures an hour, and a busy writer makes about one decision a minute, not one per batch. Nothing is audited differently. A permission that policy takes away reaches the writer's sealing within 50 s at most. `DecideResponse` has a new `expires_at`, the expiry of the sealed grant (policy sets it on an allow; a policy that leaves it out gives a grant that serves one batch). The writer's stream retry backs off from 1 s to 30 s and starts again from 1 s after a sealed batch, so a writer whose key@ is locked makes about 124 tries an hour, not 3,600, and recovers within 30 s of the unlock (REQ-AUDIT-180 to REQ-AUDIT-183, still partial until a board is checked for an idle hour; ADR 0007, ADR 0029). The indexer keeps its grant the same way (for the expiry policy states less 10 s), where it kept it for a fixed 30 s, which a poll of 30 s or more never reached: each pass decided again, wrote a record and found it on the next pass, for ever. **Breaking:** `indexer --poll-secs` is now 1 to 30 (it was 1 to 3600), because a poll above the 50 s a grant is presented can never end that loop; the default of 5 s is unchanged. Deploy policy, the writer and the indexer together: an older policy gives no expiry, the new writer then asks in every batch as before, and the indexer keeps the grant 30 s, which is quiet only at a poll of about 15 s or less. A refusal of key@ that does not name the grant (a tenant whose evidence key is gone) no longer drops the held grant, so a batch that cannot be sealed costs no decision per retry.
- New recipes `boards-firewall`, `boards-firewall-confirm`, `boards-firewall-remove`, `boards-firewall-check` and `boards-firewall-reboot-check` restrict rqlite's ports on one board at a time (`SLUIS_FIREWALL_BOARDS`): the Raft port (4002) to the loopback interface, the boards of `SLUIS_BOARDS` and one administration host (`SLUIS_FIREWALL_ADMIN_HOST`; empty means that host gets no access), the client port (4001) to the loopback interface and the administration host. rqlite 10.6.6 needs no 4001 between the boards (measured with three nodes). The rules are a table of their own (`inet sluis_rqlite`) that only drops those two ports, with no default deny and no change to firewalld, ufw or any other rule; the boot unit follows `nftables.service`, which would flush it. An apply arms a dead-man timer, loads the rules and keeps nothing until a confirm has proved ssh, a whole rqlite cluster and the peers' reach; a confirmed board loads the rules at boot, before `rqlited`, and fails open if it cannot (a stance for the test installation). `boards-status` now fails for a board without the rules. This narrows who can reach rqlite; it adds no TLS and no authentication. Nothing has been applied to a board yet (REQ-DEPLOY-046).
- After the first rollout of the rqlite firewall on three boards: `boards-smoke` over more than one board no longer fails at its cross-check (it looked for the earlier node's name in the `DataKeyWrap` ids, which are hashes; it now requires every item the earlier board read, at its version or a newer one). `boards-firewall-reboot-check` no longer needs the administration host cleared: with one set and no `SLUIS_FIREWALL_OUTSIDE_HOST` it proves the boot and the table, says the stranger half was NOT RUN and does not fail, while `boards-firewall-check` still fails as not proven. `boards-deploy` refuses a board without `/usr/sbin/nft`, before it sends anything. The YubiKey PIV driver logs the refusal of `BeginPinRelease` on an unlocked driver (key@ asks every 30 s) as a debug line, not a warning every 30 s. `docs/requirements/attestations.yaml` entries may carry `agent_run: true`.
- `boards-smoke` step 3, the audit trail, no longer fails on a board that has run for a day or more with `key Open: permission_denied, reason "grant"`. The step plays the indexer, which opens the records of the run under a grant of `audit.index` from `policy`; a grant lives 60 seconds, and the step read every record of the log, thousands on such a board, from the first with the one grant it asked for first, so key@ refused the grant part of the way. The step now reads from the newest record in batches of 64, stops when it has the records of its run, and asks `policy` for a new grant when its grant is half its life old or key@ refuses it as run out, as the indexer does. key@ and the grant are unchanged (REQ-AUDIT-184, REQ-AUDIT-185).
- The writer's state no longer grows with the traffic. It held every record id of 14 days in one object, which a board filled to 4,178,767 bytes (64,287 ids), 15,537 below the 4 MiB the blob driver takes in a request; the next seal, and then the adoption of the entries a crash left, were refused (`blob put: resource_exhausted: request body size exceeds limit 4194304`) and the writer restarted in a loop. The state now holds at most about 1,280 recent ids and names write-once segments below `state/seen/` that hold the older ones, one hour of UUIDv7 time each; a check reads the segments of the id's hour only, and a segment that is missing or changed stops the writer with an error that names it. A state of the old format is read once, and the first commit after a start spills it, so a board in the loop recovers by itself on its next start, without a hand action and without losing or doubling an entry (REQ-AUDIT-178, REQ-AUDIT-179, ADR 0029). **Breaking:** a record id must be a lower-case UUIDv7, as ADR 0029 always said; a message whose record time or id time is older than 14 days, more than an hour ahead of the writer's clock, or whose id time is more than two minutes from its record's, is quarantined (`stale`, `future`, `schema`); the state is of format 2, which a writer of the first format refuses, so a rollback after the first commit cannot start; and the writer applies the 14-day and one-hour checks and forgets ids only on a clock that the kernel calls synchronised and that has not stepped; on any other clock (including one the kernel does not answer for) it accepts and remembers, forgets nothing, and its seal entry says `time_checks` did not run and why. The writer's unit allows `adjtimex` and has `ProtectClock=no` so that it can see the kernel's answer (it could not: the seal entries of the boards said `observed: false`); redeploy the units for it. The Go and Rust emitter kits follow the clock again when the last id is more than a minute ahead of it. A damaged segment stops the writer until the object is restored; no tool rebuilds one yet. The deploy's "every unit is up" is a point-in-time check (`docs/runtimes/bare-metal.md`).
- key@ no longer writes audit records for waiting. A board with a PIN release request that no peer could answer wrote about 16,000 failure records an hour: each pass of the releasing loop, once a second, made seven lookups that found nothing (the answer, and three `KeyRevocation` ids each for its own keys and the peer's), and store@ audits every refusal. key@ now lists `PinRelease` and `KeyRevocation` in place of those lookups, for the releasing side, the requesting side and the revocation check of every Sign (which wrote one refusal per audit checkpoint). A releasing pass that answered nothing and saw no new request doubles its wait from 500 ms to 10 s (2 s while the board's own driver is locked, so a board a person unlocks answers its peers within 2 s); a new request or an answer starts it again from 500 ms, and a node that has just taken a PIN passes at once, so a peer release takes what it took before (REQ-KEYS-229 to REQ-KEYS-232). The revocation listing is linearizable like the lookup it replaced: `ListRequest` has a `consistency` field and the item port's `QueryRequest` a `linearizable` flag (REQ-KEYS-233, REQ-DATA-113). A listing that leaves it unset is read as before, at rqlite's `weak` level, so nothing else changes in cost; a driver that cannot give the level refuses and never answers a weaker one. Deploy store@ and the driver before key@: an older store@ or driver ignores the field and reads weak without an error. A board that is idle, locked or waiting for a peer should write at most 60 audit records an hour (REQ-AUDIT-180; the writer's part, the seal of its own policy decision, is the entry above).
- The boards deploy reads the lock of a card board from its card driver, with the new read-only `sluis node status NODE` (`node NODE is locked` or `unlocked`; no PIN is read, sent or printed), and not from a journal (REQ-DEPLOY-043). `SLUIS-BOARD-STATE: ok` now means every unit is up and the driver is unlocked; a locked board is `locked` (exit status 0, with the `boards-unlock` hint) whether its units are all active or only the ones that wait for key@ restart, and a unit with a fault of its own, or a lock that cannot be read, is `failed`. `boards-status` prints `board <board>: locked` or `unlocked` for each board, and `boards-unlock` asks the driver again afterwards, names a unit that systemd gave up on, and fails if a unit still restarts. **Breaking** for the generated units: an actor unit has no start limit (`StartLimitIntervalSec=0`, REQ-DEPLOY-044) and backs its restarts off from 2 s to 30 s (`RestartSteps=5`, `RestartMaxDelaySec=30`, systemd 254's; the deploy drops them on an older board), where it had 40 starts in 120 s, which a unit that waited for a locked driver exhausted (`start-limit-hit`) and which no unlock undid; deploy again to apply it. The docs say that the first board of a re-signed `KeyPlan` has to be unlocked by hand, because its peers still hold the old plan.
- key@ could not publish a PIN release: its action table lacked `key.pin.release`, `key.pin.unlock` and `key.revoke`, so the blocking audit fact of a release failed (`no action "key.pin.release" in the action table`) and a locked peer stayed locked. The three are in the table (6003 / 99, named "PIN Release", "PIN Unlock" and "Revoke") and `key.revoke` is in the audit catalogue of the local installation. A blocking emit that fails still fails the call. Tests now find every `Action` constant of keyd in the source and require it in key@'s table and in the catalogue, and the same for the other Go actors.
- **Breaking** for a reader of the audit log that keys on class: `key@` records `key.data_key.make` and `key.wrap.write` as OCSF 3004 Entity Management / 1 Create, where it recorded 6003 API Activity / 1 (ADR 0030, "The class mapping": a key created is 3004; owner decision AC1 A, 2026-11-06). The action names and fields are unchanged, so the audit catalogue is too; the other facts of `key@` stay 6003. Records already in a log keep the class they were written with.
- The credential driver of store@ accepts the credentials directory that systemd 259 makes where the filesystem has ACLs (REQ-DATA-112): `root:root` `0550`, files `root:root` `0440`, and a POSIX ACL that grants the service user the read. It refused it ("the credentials directory must be owned by the uid of this process"), so store@ had no secret source and key@ and writer@ looped on `unavailable: store`. Root may own the directory and its files only when the directory is the one `$CREDENTIALS_DIRECTORY` names (the same inode once canonicalised); a `--dir` elsewhere still has to be the driver's own uid's. Group and others still cannot write, others cannot read, and a group read is allowed only for a file with an access ACL in that directory that names no user but the driver's own uid and no group that reads. `credential check` now also reads every credential in the directory by the rules of a read and prints no value. The boards deploy now waits up to 60 s for each unit to be `active (running)` with a restart counter that has not changed for about 6 s, and fails a unit that restarts, with the last lines of its journal since the start; a card board that is only locked, waiting for its PIN (the state line `SLUIS-BOARD-STATE: locked`, and only when every other unit that has not settled depends on key@), ends `locked` with exit status 0 and names `boards-unlock` (it was a failure, and "verify: ok" only ever meant that the unit files read well). The os-containers CI jobs run the real credential driver in its unit.
- The `Workload` entity of the policy schema has two new optional attributes, `event` (GitHub's `event_name`) and `ref_type`, and the built-in layer forbids `artifact.sign` for a workload whose ref begins `refs/pull/`, whose event begins `pull_request` (`pull_request_target` included) or is `issue_comment`, `workflow_run` or `merge_group` (owner decision W1 A, 2026-11-06: these can run pull-request code), or that comes from `github-oidc` with no event (REQ-WORKLOAD-007), whatever the operator's policy permits. `exchange` reads the job claims of a verified GitHub Actions token (`repository`, `ref`, `ref_type`, `event_name`, `environment`) and refuses a `github-oidc` proof with no `event_name`. The signing API does not ask `policy` yet (#890): the guard holds from the first question. **Breaking:** `exchange` now answers `invalid_request` with the reason `claims` to a `github-oidc` proof that has no `event_name` (GitHub sends one in every token). The built-in forbid affects no existing policy that is not about `artifact.sign` for a pull request. The local installation's vectors carry `event: push` on their `github-oidc` workloads for realism; `cedar run-tests` checks them against `local.cedar` only, so the built-in rule does not apply to them and the change was not required.
- The writer and `sluis audit verify` take the checkpoint body, the tile paths and the tile entries of the audit log from `filippo.io/torchwood` and `golang.org/x/mod/sumdb/note`, and keep only the signature type 0x02 key and the adapter that has key@ sign (REQ-SEC-018, partly). Nothing on the wire changes: logs written before still verify, and logs written now verify with the former reader (tests/testdata/audit-log/old-writer). The `checkpoints/<size>` history is specified on [Checkpoint history](docs/reference/checkpoint-history.md), with limits that `audit verify` now enforces: names of at most 19 digits and checkpoint files of at most 1 MiB (`.name`, `.length`); the number of checkpoints has no limit, and `audit verify` reads the directory in batches, one file at a time, in ascending order of size, so the same log always gives the same refusal. A checkpoint with a blank extension line, which `audit verify` took before, is now refused as `.format`.
- The boards deploy (`deploy/boards`) is ready for fresh Ubuntu 26.04 and Rocky 10 boards. `just boards-rqlite` installs rqlite on each board from the upstream v10.6.6 release package, pinned by sha256 in `deploy/boards/rqlite.pins`, with a drop-in of `rqlited.service` that sets the addresses and, on every node, `-bootstrap-expect N` and `-join` with the Raft addresses of all N boards (no node can start a cluster of its own, so a wiped board rejoins the cluster of the others; the node id is the Raft address), starts all nodes and then waits for each to be a ready voter and for `/nodes` to hold N nodes; the store drivers wait for `rqlited.service`. `just boards-unlock` gives the PIN to a board's card driver from standard input, never as an argument; `cli/sluis` is staged to `/opt/sluis/bin/cli/sluis` for it. `SLUIS_BOARD_SSH_OPTIONS` carries extra ssh arguments (a known-hosts file for a reinstalled board) into the scripts and the smoke program. `SLUIS_BOARDS_PROFILE=m1` deploys the twelve executables of the M1 spine. `boards-deploy` refuses a board without `tar` before it sends anything, and `boards-deploy` and `boards-smoke` end with an AVC check (`just boards-avc`) on a board with SELinux enforcing, which fails on an enforced denial in the domain of the units or the card service, of an executable of the deploy, or on a sluis or rqlite path, and when auditd is not recording. The key-switch guard reads the data-key count with the same bash `/dev/tcp` reader as rqlite's readiness, since the boards have no curl. `boards-undeploy` and `boards-status` look after rqlite. rqlite has no TLS and no authentication on the boards yet: put a firewall in front of ports 4001 and 4002 before any real PIN (REQ-DEPLOY-034 to REQ-DEPLOY-037).
- The Rust store client follows a kind: `Store::watch` (and `KeyRevocations::watch`) lists the kind, watches from the position of the listing and gives the changes as events, in order and once (ADR 0005, REQ-DATA-108). It reconnects from the last position with a backoff and says a break as an event. A resume point that store@ no longer holds is an explicit resync that carries the whole state (REQ-DATA-109); a value that does not decode or a malformed change ends the watch with an error. `exporter@` (#1453) will use it, and `entry` and `signer` can stop reading `KeyRevocation` and `SigningRing` for each call (#1362).
- `sluis key revoke --declaration` now confirms the revocation (ADR 0009, "Confirmation"; REQ-KEYS-088, partly: the edge purge and the static document wait for `exporter@`, #1453 and #1454). After key@ takes the declaration it fetches, as a relying party does and with no cache-buster (a plain GET, a new HTTP/1.1 connection, no proxy), the `jwks_uri` that the issuer's discovery document names (on the issuer's origin) and `entry`'s live key set from its socket, and reads both every 2 seconds for up to `--wait` (default 2 minutes) until every revoked key is absent from both in the same round. The keys are those of the signed declaration, found by `kid` and by RFC 7638 thumbprint, and the answer is read strictly (a duplicate or case-variant member is `could not tell`). It prints `confirmed absent`, `still listed` or `could not tell` for each address, with the issuer, its source and the number of keys read, then warnings, then `confirmed` (exit 0) or `not confirmed` (exit 5, new): an address it cannot read is never counted as absent. `--issuer` defaults to the issuer that `entry` reports on its socket, `--entry-socket` to `/run/sluis/entry/<boundary>.sock`, so the command is run on a node that runs `entry`; a clean result is one sample from this host and this node. `--check` looks again without delivering anything. Before this the command always printed `not confirmed`.
- `sluis config explain DIR --bootstrap FILE [--field PATH]` prints what each setting of the bootstrap file and of the signed config documents resolves to, with its storage class, the layer that set it (`bootstrap`, `config` or `built-in`), its version (the `seq` of the document) and its source (the document as the audit fact of a start names it, `Kind:seq:sha384`) (REQ-OPS-023, partly: the `--live` layers and the built-in layer of the documents are not built, #1450). It runs the store executable as a helper, like `config check` (`store check --validate DIR --explain`), and explains only a set that passes its checks; a set that fails prints the failed checks and exits 3. It fails closed: store@ holds a closed table of the fields of each kind with the way each is printed, and a field it does not list is printed as its SHA-384. A credential (`secret` of an `Upstream` or an `InstallationClient`) is printed as its reference and marked; a URL has no query and no fragment; a public key of the slot map is its pin; a value longer than 256 bytes or with a control character, an invisible format character or a line separator, such as the Cedar text, is its SHA-384 (`digest: true` in JSON); a duration is shown in its largest whole unit. `--field PATH` limits the output to a subtree and a path that names nothing is a usage error. `--output json` prints `fields` beside `checks`. **Breaking:** store@ refuses at load, and `config check` with it, a URL with user information (`user:password@host`) in a boundary issuer, an upstream issuer, an exchange trust issuer or key set, or a client redirect; no fixture or example used one.
- `signer` and `entry` act on a revoked token-signing key at once (ADR 0041, REQ-KEYS-106, REQ-KEYS-107): the key set they serve lacks every kid that `KeyRevocation` lists (`entry` rebuilds its documents at most every five seconds), and `signer` never adds a revoked key to its ring, never promotes it, and refuses a `SignToken` with it on the next call (the reason `key_revoked`), where the ring was looked at again only every ten seconds. "At once" is for these two actors only: a relying party may still accept the revoked kid from its copy of `/jwks` for the key set's `max-age` (300 s) plus the edge copy, which `exporter@` is to purge (not built, #1454; `sluis key revoke` now checks for it, REQ-KEYS-088). - A replacement for a revoked token-signing key skips the 30-minute lead time when the issuer has no live key that signs (ADR 0041, "The replacement", REQ-KEYS-089), where a one-key installation signed nothing for about 30 minutes after `sluis key revoke`. The shortcut is for the case where no key of the ring that `KeyRevocation` does not list is `active` (in practice: every `active` key is revoked); a key in a state `signer` does not know counts as signing, so a rolling upgrade cannot skip the lead time, and a normal rotation, a revoked spare and another node's live key keep it. The new key is written to the ring, `active`, with the audit reason `no_active_key` on `signer.ring.add` or `signer.ring.change`, and `signer` signs with it about 6 seconds later, not at once: `entry` keeps its built key set for 5 seconds (`sluis_store::KEY_SET_CACHE`), and no token is signed before `entry`'s `/jwks` can list the key. **Not safe to rely on yet:** the replacement signs before any relying party or edge copy has its key, a copy of `/jwks` may lack it for the key set's `max-age` (300 s) plus the edge copy, and `exporter@` does not yet purge the edge copy (#1454), so `sluis key revoke` will report a stale edge copy as `still listed` for up to the 65 minutes of the stale window (REQ-KEYS-088 is partial); do not rely on `sluis key revoke` in production yet.
